# ADR-0002: где размещать базу данных TimeCapsule

- Статус: принято
- Дата: 2026-10-12
- Контекст: ЛР3, перенос приложения из ЛР2 (default VPC, всё на одном сервере) в собственную VPC `timecapsule-dev-vpc`

## Решение

База данных размещается на **отдельном сервере `db-server` в приватной подсети `private-a`**,
без публичного адреса, с именем `db.timecapsule.internal` в приватной зоне Route 53.
Приложение (`app-server` в `public-a`) обращается к базе по этому имени.

## Варианты

### 1. На одном сервере с приложением (как в ЛР2)

PostgreSQL слушает `localhost` на том же экземпляре, что и nginx/PHP.

- Плюсы: нет сетевой настройки, нет отдельного тарифа за второй экземпляр, низкая задержка.
- Минусы: компрометация веб-слоя (= RCE через приложение) сразу даёт доступ ко всей БД;
  масштабировать приложение и БД по отдельности нельзя; обновления ОС/пакетов затрагивают обе роли.

### 2. Отдельный сервер в публичной подсети

`db-server` в `public-a` с публичным IP, порт 5432 открыт только для `web-sg`.

- Плюсы: изоляция процессов и ОС; удобно подключаться с внешних инструментов.
- Минусы: БД имеет маршрут в интернет и публичный адрес — атакующему достаточно одного
  промаха Security Group (или забытого правила `0.0.0.0/0`), чтобы получить прямую
  сетевую поверхность атаки на данные; уязвимости PostgreSQL становятся remotely exploitable;
  нарушается принцип минимальной привилегии на уровне сети.

### 3. Отдельный сервер в приватной подсети (выбран)

`db-server` в `private-a`, без публичного адреса, без маршрута `0.0.0.0/0` в `private-rt`
(NAT Gateway — только временный, на время `nixos-rebuild`/обновлений). Доступ по 5432 —
только из `web-sg` (Security Group), вход — только пользователь `timecapsule` в базу
`timecapsule` (`pg_hba.conf`, scram-sha-256).

- Плюсы: интернет физически не может инициировать соединение к БД (нет адреса и маршрута);
  тройная защита (маршрут/адрес → Security Group → pg_hba) соответствует defense-in-depth;
  БД масштабируется и обновляется независимо.
- Минусы: нужен отдельный экземпляр (~$3/мес при 3 ч/день) и способ ставить обновления
  без постоянного выхода в интернет — временный NAT Gateway (~центы за сессию, но
  forgotten NAT ≈ $1.25/сутки); SSH только через bastion (дополнительный hop).

## Последствия

- **Обновления без постоянного выхода в интернет.** `db-server` не может сам ходить в
  `cache.nixos.org`/DNF. Пакеты накатываются циклом из отчёта (задания 6 и 13):
  поднять временный NAT Gateway в `public-a` (EIP → `create-nat-gateway` → `wait` →
  маршрут `0.0.0.0/0` в `private-rt`), выполнить `nixos-rebuild switch --flake .#db`
  (или `dnf update` на нативном стеке), удалить маршрут и шлюз (`delete-route` →
  `delete-nat-gateway` → `wait nat-gateway-deleted`), освободить Elastic IP с ретраями.
  Стоимость сессии —
  центы; главный риск — забытый шлюз ($1.25/сутки), поэтому удаление входит в
  обязательный чек-лист завершения работы и в скрипт `11-teardown.sh`.
- **Elastic IP у app-server.** Публичный адрес экземпляра меняется после stop/start,
  а `APP_URL` и закладки пользователей должны оставаться стабильными. Elastic IP
  ($0.005/ч, платится всегда, даже для остановленного сервера) закрепляет адрес за
  `app-server`. Bastion такого адреса не требует: его HostName обновляется в
  `~/.ssh/config` при каждом запуске — неудобно, но бесплатно.
  Когда перед приложением появится Application Load Balancer, Elastic IP перестанет
  нужен: фронтендом станет DNS-имя балансировщика, а сам балансировщик динамически
  привязывается к подсетям; EIP на одиночном сервере помешает быстрой замене экземпляра.
- **DNS вместо сырых адресов.** Приватная зона `timecapsule.internal` позволяет
  пересоздать `db-server` с другим IP и обновить одну A-запись, а не `.env` на каждом
  приложении; TTL 60 с быстро разносит смену адреса внутри VPC.
- **Экономика.** Три t3.micro ≈ $10/мес при 3 ч/день, диски ≈ $7, EIP app ≈ $11,
  Route 53 приватная зона $0.50/мес — итого ≈ $31 за три месяца (по оценке лабы),
  если NAT живёт только во время обновлений.
